# Вимоги до системи — SSI Course Platform

Окремий документ вимог для сайту курсів (`ssi-course-platform`) — логічно окремого застосунку від SSI Identity dApp (`Decentralized_Identity_Verification_System_SSI`), що виступає стороннім "relying party" відносно вже наявної SSI-ідентичності користувача.

## Функціональні вимоги

| # | Вимога |
|---|--------|
| F-1 | Користувач може переглянути каталог курсів без підключення гаманця (список читається з бази даних на сервері). |
| F-2 | Користувач може підключити MetaMask; при кожному підключенні MetaMask завжди показує вибір акаунта (не повертає мовчки раніше авторизований). |
| F-3 | Система перевіряє наявність зареєстрованої SSI-ідентичності для підключеної адреси через `CourseRegistry.isVerified(address)`, який читає стан наявного `BasicIdentityRegistry` без його модифікації. |
| F-4 | Якщо адреса не верифікована, користувач може пройти верифікацію без переходу на інший сайт: сайт відкриває SSI-додаток у popup-вікні; після успіху popup сам сповіщає сайт курсів і закривається. |
| F-5 | Верифікований користувач може записатися на курс — підписує транзакцію `registerForCourse(courseId)` у смарт-контракті `CourseRegistry`. |
| F-6 | Після підтвердження транзакції backend незалежно перевіряє факт реєстрації напряму в блокчейні (`getCourseRegistration`), і лише після цього робить запис у базу даних — фронтенд-повідомлення про успіх ніколи не є єдиною підставою для запису. |
| F-7 | Для вже зареєстрованих курсів кнопка запису показує стан "Ви записані" замість повторної дії. |

## Нефункціональні вимоги

| # | Категорія | Вимога |
|---|-----------|--------|
| NF-1 | Безпека | Приватні ключі користувача ніколи не залишають MetaMask — усі транзакції (верифікація читання, запис на курс) підписуються/виконуються локально, з боку сайту й сервера йдуть лише запити на читання. |
| NF-2 | Довіра до даних | База даних (`Enrollment`) — лише кеш для швидкого відображення списку; єдине джерело правди — стан блокчейну (`CourseRegistry`), який перевіряється незалежно і клієнтом (перед показом кнопки), і сервером (перед записом у БД). |
| NF-3 | Сумісність | Сайт не змінює й не потребує зміни вже наявного контракту `BasicIdentityRegistry` — `CourseRegistry` лише читає його публічний стан через незмінне посилання, задане при деплої. |
| NF-4 | Переносимість ідентичності | Одна й та ж SSI-ідентичність, зареєстрована один раз у SSI-додатку, придатна для верифікації на будь-якій кількості сторонніх сайтів (relying parties) без повторної реєстрації — на відміну від традиційного облікового запису, прив'язаного до конкретного сайту. |
| NF-5 | UX | Верифікація незареєстрованого користувача не вимагає ручного перемикання між вкладками браузера і повернення назад (popup + postMessage замість full-page переходу). |

## User Stories

**US-1:** Як студент з уже зареєстрованою SSI-ідентичністю, я хочу підключити MetaMask на сайті курсів і одразу побачити, що я верифікований, щоб записатися на курс без повторної реєстрації десь ще.

**US-2:** Як новий користувач без SSI-ідентичності, я хочу пройти верифікацію прямо з сайту курсів (через popup-вікно), щоб не втрачати контекст сторінки і не шукати вручну інший сайт.

**US-3:** Як розробник/аудитор системи, я хочу бути впевненим, що backend ніколи не довіряє клієнтському сигналу про успішну реєстрацію на курс, а завжди перевіряє транзакцію напряму в блокчейні, щоб унеможливити підробку запису без реальної on-chain дії.

### Acceptance Criteria для US-1

- Кнопка "Увійти через MetaMask" завжди показує вибір акаунта в розширенні (навіть якщо сайт раніше вже мав доступ до іншого акаунта).
- Після підключення сайт читає `isVerified()` для підключеної адреси напряму з блокчейну через RPC, видимий у DevTools → Network.
- Якщо адреса верифікована — кнопка "Записатися" стає активною для курсів, на які користувач ще не записаний.
- Після успішного `registerForCourse()` і підтвердження сервером кнопка змінюється на "Ви записані ✅" без перезавантаження сторінки.

### Acceptance Criteria для US-2

- Кнопка "Верифікувати через SSI" відкриває popup-вікно синхронно з кліку (не блокується popup-блокером браузера).
- Popup показує звичний інтерфейс SSI-додатку; якщо адреса, підключена всередині popup, уже зареєстрована — popup сам закривається протягом ~1.5 с після сповіщення.
- Сайт курсів після отримання сповіщення від popup самостійно повторно перевіряє `isVerified()` — і лише після цього оновлює статус на "Верифіковано", а не одразу за фактом отримання повідомлення.
- Повідомлення від будь-якого джерела, окрім `https://bakalavr.vercel.app`, або з невідповідною адресою, ігнорується.

## Use Case Diagram

**Актори:** Студент (через MetaMask), `CourseRegistry` (Ethereum, цей проєкт), `BasicIdentityRegistry` (Ethereum, наявний SSI-додаток, лише читання), SSI-додаток (relying-party popup), Backend (Next.js API Routes + Postgres).

| Актор | Сценарій |
|---|---|
| Студент | Переглянути каталог курсів |
| Студент | Підключити MetaMask |
| Студент | Пройти верифікацію через popup SSI-додатку |
| Студент | Записатися на курс |
| Студент | Переглянути статус власних записів на курси |
| Backend | Незалежно перевірити реєстрацію на курс в блокчейні перед записом у БД |
| `CourseRegistry` | Прочитати стан `BasicIdentityRegistry` для перевірки `isVerified()` |
